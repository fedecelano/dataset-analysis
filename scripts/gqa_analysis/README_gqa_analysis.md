# GQA Dataset Analysis

This directory contains scripts for inspecting the **original** and **cleaned** GQA scene-graph datasets. The analyses cover annotation statistics, label distributions, bounding-box geometry, image/annotation consistency, and qualitative examples.

The scripts support dataset exploration and quality assessment before downstream probing experiments. They **do not clean datasets, change source annotations, remove images, or train models**. Cleaning and probing are handled in separate directories. Running the scripts may create or overwrite files under `outputs/gqa_analysis/`.

All five scripts select the annotation version with `--dataset original` or `--dataset cleaned` (default: `original`). Both versions use images from **`data/gqa/images/`**; the cleaned mode does not require a separate copy of the images. Output folders are created as needed.

## 2. Requirements and execution

Use Python **3.10 or later** and install the external dependencies:

```powershell
python -m pip install numpy pandas matplotlib Pillow
```

| Package | Scripts |
| --- | --- |
| `numpy`, `pandas` | `analyze_gqa_bboxes.py`, `plot_frequencies.py` |
| `matplotlib` | `analyze_gqa_bboxes.py`, `plot_frequencies.py`, `visualize_gqa_scenegraphs.py` |
| `Pillow` (`PIL`) | `visualize_gqa_scenegraphs.py` |

From the project root, run:

```powershell
python scripts/gqa_analysis/check_gqa_images.py --dataset original
python scripts/gqa_analysis/inspect_gqa.py --dataset original
python scripts/gqa_analysis/analyze_gqa_bboxes.py --dataset original
python scripts/gqa_analysis/visualize_gqa_scenegraphs.py --dataset original
python scripts/gqa_analysis/plot_frequencies.py --dataset original
```

Replace `original` with `cleaned` to inspect the cleaned annotations. Paths inside the scripts are resolved relative to their own locations, so they do not depend on the terminal's working directory. The commands above assume the terminal is at the project root.

**Dependency between scripts:** `plot_frequencies.py` reads the three frequency CSVs generated by `inspect_gqa.py` for the **same dataset version**. The remaining scripts can run independently when their input files are available.

## 3. Scripts and outputs

### 3.1 `inspect_gqa.py` — Annotation statistics and vocabularies

Reads the train and validation scene graphs and counts images, object instances, attribute occurrences, relation occurrences, and unique labels. It also compares the train and validation vocabularies.

Input: `data/gqa/annotations/{train,val}_sceneGraphs.json` or the equivalent files under `data/gqa_cleaned/annotations/`.

Outputs under `outputs/gqa_analysis/<dataset>/tables/`:

| File | Contents |
| --- | --- |
| `dataset_summary.csv` | Image and annotation totals, plus unique-label counts, by split |
| `vocabulary_overlap.csv` | Shared and split-exclusive vocabulary sizes by label type |
| `vocabulary_differences.csv` | Labels occurring exclusively in one split and their counts |
| `class_frequencies.csv` | Object-class occurrence counts in train and validation |
| `attribute_frequencies.csv` | Attribute occurrence counts in train and validation |
| `relation_frequencies.csv` | Relation occurrence counts in train and validation |

Each frequency is an **annotation-occurrence count**, not the number of images containing the label. Labels are preserved as written in the source JSON: no normalization, synonym merging, or semantic validation is performed. Relations are counted from the relation lists attached to objects.

### 3.2 `plot_frequencies.py` — Label-frequency plots

Reads the three frequency CSVs from `inspect_gqa.py` and saves two figures under `outputs/gqa_analysis/<dataset>/plots/`:

| File | Contents |
| --- | --- |
| `frequency_distributions_combined.png` | Rank-frequency curves for objects, attributes, and relations, with train and validation ranked independently and a logarithmic frequency axis |
| `top_labels_relative_combined.png` | Train/validation relative frequencies for the top-N labels selected by **training** occurrence count |

The rank-frequency plots compare distribution shapes: a given rank in train need not refer to the same label as that rank in validation. Zero counts are excluded from these log-scale curves.

For the top-N plots, percentages use the total number of annotations **of that label type within the corresponding split** as the denominator. They are not percentages of images. If a split has no annotations, its percentages are undefined and the figure displays an explanatory message.

The default is 30 labels. To change it:

```powershell
python scripts/gqa_analysis/plot_frequencies.py --dataset cleaned --top-n 20
```

The script checks for missing columns, missing or duplicate labels, and invalid counts in its input tables.

### 3.3 `check_gqa_images.py` — Image and split-ID consistency

Compares scene-graph IDs against supported image files directly inside `data/gqa/images/`. It detects missing files, overlapping train/validation IDs, and multiple files sharing an image ID. In cleaned mode, it additionally compares scene-graph IDs with `data/gqa_cleaned/image_ids/train.txt` and `val.txt`, including repeated IDs within each list.

Supported file extensions are `.jpg`, `.jpeg`, and `.png` (case-insensitive). The scan is **not recursive**, and the script does **not** attempt to decode images.

Outputs under `outputs/gqa_analysis/<dataset>/tables/`:

| File | Contents |
| --- | --- |
| `image_integrity_summary.csv` | Metric/count summary of files, unique IDs, split overlap, and (in cleaned mode) ID-list consistency |
| `image_integrity_issues.csv` | Per-ID findings with `issue_type`, `split`, `image_id`, and `details` |

The summary is also printed to the terminal. An image that lacks a scene graph in the two analyzed splits is **informational**, not automatically an error: the image collection may include other GQA splits. Summary counts generally refer to unique IDs; the issues CSV can have separate rows for the same missing ID when it appears in both splits. Duplicate-ID-list counts refer to the number of **distinct IDs repeated**, not the number of extra lines.

### 3.4 `analyze_gqa_bboxes.py` — Bounding-box quality and size

Classifies every annotated bounding box without editing the scene graphs:

| Status | Definition |
| --- | --- |
| `valid` | Finite geometry, positive image and box dimensions, and the box lies completely inside the image |
| `clippable` | Finite geometry and positive dimensions; the box extends outside the image but intersects it with strictly positive area |
| `invalid` | Non-finite/invalid geometry, non-positive dimensions, or no positive-area intersection with the image |

Negative `x` or `y` coordinates do **not** automatically make a box invalid. There is no percentage-overflow threshold. The analysis treats recoverable boxes as `clippable` but **does not actually clip or rewrite annotations**. It also checks calculated endpoints for non-finite values.

For `valid` and `clippable` boxes, relative size is computed from the intersection of the box with the image:

```text
relative area = clipped bounding-box area / image area
```

Seven left-inclusive size bins are used: `<0.1%`, `0.1–1%`, `1–5%`, `5–10%`, `10–25%`, `25–50%`, and `≥50%` (the last bin includes 50% and above as implemented). The internal bins are `[0, 0.001, 0.01, 0.05, 0.10, 0.25, 0.50, inf)`.

Outputs:

| File | Contents |
| --- | --- |
| `tables/bbox_quality_summary.csv` | Counts and percentages for all three statuses among **all** boxes, by split |
| `tables/bbox_size_distribution.csv` | Size-bin counts and percentages among **valid and clippable** boxes only |
| `plots/bbox_size_distribution.png` | Train/validation comparison of usable-box size distributions |

The script checks that every usable box receives a size-bin assignment. Clipping or removing invalid boxes, if desired, belongs to the separate cleaning pipeline.

### 3.5 `visualize_gqa_scenegraphs.py` — Qualitative examples

Selects four distinct train images and four distinct validation images, one for each profile:

| Profile | Selection emphasis |
| --- | --- |
| `simple` | Low combined object, attribute, and relation density |
| `attributes` | High attribute density, with at least one attribute |
| `relations` | High relation density, with at least one relation |
| `complex` | High combined annotation counts |

The selection uses ranks relative to **eligible images in the same split**, not fixed thresholds defining scene complexity. Profiles are selected in the fixed priority order `simple`, `attributes`, `relations`, `complex`, choosing the highest-scoring unused candidate for each. Ties are broken by image ID. This is a deterministic **greedy** selection, not a globally optimal assignment and not a random or representative sample.

Eligible candidates must have **2–14 objects**, no more than **36 attribute occurrences**, no more than **24 relation occurrences**, a corresponding local image, and relation targets resolvable within the scene graph. For selected candidates, the script checks that the image can be decoded; unreadable selections are excluded and selection is repeated. These limits are intended to keep complete tables reasonably readable, but very long text may still affect layout.

Outputs under `outputs/gqa_analysis/<dataset>/qualitative_examples/`:

```text
overview.png
train_simple.png
train_attributes.png
train_relations.png
train_complex.png
val_simple.png
val_attributes.png
val_relations.png
val_complex.png
```

`overview.png` shows train examples in the first row and validation examples in the second. Each detailed figure shows an image with numbered bounding boxes above an object/attribute table and an instance-level relation table. Object numbers link the boxes to the tables. The displayed box coordinates come directly from the annotations and are not clipped. No `.txt` annotation files are created. The nine named PNGs may be overwritten on repeated runs; unrelated existing files in the destination directory are not deleted.

The image lookup supports `.jpg`, `.jpeg`, and `.png` extensions case-insensitively. When several files share an ID, the visualization prefers `.jpg`, then `.jpeg`, then `.png`; the integrity-check script reports such duplicates separately.

## 4. Recommended workflow

For each dataset version:

1. Run `check_gqa_images.py` to inspect image availability and split/list consistency.
2. Run `inspect_gqa.py` to generate statistics and the frequency tables.
3. Run `analyze_gqa_bboxes.py` to inspect bounding-box geometry.
4. Run `visualize_gqa_scenegraphs.py` to generate qualitative examples.
5. Run `plot_frequencies.py` after `inspect_gqa.py` to visualize label distributions.

Repeat with `--dataset cleaned` to inspect the cleaned annotations. Original and cleaned outputs are written to separate folders. The scripts do not generate a unified original-versus-cleaned comparison report.

## 5. Interpretation and reproducibility

- **Read-only datasets:** the scripts do not modify images, scene graphs, or image-ID lists. They do write output files, potentially overwriting previous figures or tables for the same version.
- **Dataset versions:** `original` and `cleaned` refer to annotation versions; both resolve image files from `data/gqa/images/`. The presence of a cleaned annotation directory does not by itself establish which cleaning steps have been performed.
- **Annotation counts:** frequencies measure occurrences in the available annotations, not image-level prevalence or semantic correctness.
- **Image integrity:** matching IDs and file paths do not prove that files are decodable or annotations correct. The qualitative script decodes selected images only.
- **Bounding boxes:** geometric usability does not prove that a box correctly localizes the intended object.
- **Qualitative examples:** samples are selected to contrast annotation profiles and are not statistically representative.
- **Probing:** this directory does not create probing splits, extract layer-wise features, or train/evaluate probes.
- **Reproducibility:** record the dataset version, script revision, command-line arguments, and preprocessing performed before using plots or tables in the thesis. File content and candidate eligibility can affect selected examples.

The scripts assume the expected GQA scene-graph structure for individual records; they do not perform full schema validation of every object, attribute, or relation.
